# Example: Migrating ADP Workflow Exports to AgentKit Runtime

## Overview

This example shows how to migrate an application package exported from ADP Workflow into a VeADK project that can be deployed to AgentKit Runtime.

An ADP Workflow export package is not a Python project that can be published directly to AgentKit Runtime. Its application information, prompts, node orchestration, and runtime configuration are mainly stored in JSON files exported from the platform. For Workflow projects generated by this type of low-code platform, you can combine the AgentKit Migration command with AgentKit Codex Sandbox to complete an automated migration: use `agentkit migrate any_input --framework any create` to create a migration task and submit the export package. The remote Codex Sandbox then analyzes the application configuration, workflow structure, and visible behavior, and generates a VeADK project deployable to AgentKit Runtime.

The input for this example is a hotel booking ADP Workflow application. The source application uses a single workflow chain, `START -> LLM -> ANSWER -> END`. Its core behavior is to generate hotel booking plans based on user needs, and to recommend `北京饭店` in the Beijing hotel scenario. The migration output is a VeADK project converted by Codex.

This document guides you through export package preparation, remote migration task creation, result query and download, migration artifact inspection, and publishing to AgentKit Runtime with `agentkit release`.

## Core Features

This example covers the complete migration path from an ADP Workflow export package to an AgentKit Runtime project:

- Read application metadata, workflow structure, prompts, and visible behavior from the ADP Workflow export package.
- Convert a single-workflow application into a VeADK / AgentKit Runtime project through the remote Codex Sandbox.
- Generate deployable configuration, runtime code, a migration report, and evaluation samples, with support for continuing to run `agentkit release`.
- Preserve capability boundary descriptions in the migrated artifacts for external dependencies, tool calls, or real booking capabilities that do not exist in the source application. Do not fabricate external call results.

## Original Input

The input directory is `any_input/`, which contains a Workflow application package exported from the ADP platform. To prepare it, select the target application in the ADP application list and export it, download the ZIP file and unzip it, then place the entire extracted export directory into `any_input/`.

The input directory in this example is:

```bash
any_input/
├── metadata.json
└── app/
    ├── metadata.json
    ├── app_config/
    │   ├── app_synonyms.json
    │   ├── app_variable.json
    │   ├── base_config.json
    │   └── metadata.json
    └── workflow/
        ├── metadata.json
        ├── workflow_config.json
        └── workflow_example.json
```

The source application information is roughly as follows:

- Application name: `workflow_agent_example`
- Agent name: `酒店预定agent`
- Workflow mode: `single_workflow`
- Workflow chain: `START -> LLM -> ANSWER -> END`

## Migration Flow

```text
ADP Workflow export ZIP
    |
    v
Unzip and place it into any_input/
    |
    v
agentkit migrate any_input --framework any create
    |
    v
Remote Codex Sandbox analyzes the export package structure and workflow behavior
    |
    v
VeADK / AgentKit Runtime project
    ├── .agentkit/agentkit.yaml
    ├── assistant/agent.py
    ├── main.py
    ├── migration_metadata.json
    ├── convert_report.md
    └── eval/
```

## Directory Structure

```bash
workflow/
├── .env.example       # Environment variable example
├── README.md          # Chinese documentation
├── any_input/         # Input directory for the ADP Workflow export package
```

All subsequent commands are executed in the `ADP/workflow/` directory. `any_input/` is the source project input directory. `--output ../any_output` is resolved relative to `any_input/`, and the migration artifacts are written to the `any_output/` directory at the same level as `any_input/`.

## Start Remote Migration

### Check the AgentKit CLI Version

First make sure that the TypeScript version of the AgentKit CLI is installed locally, and that its version is no lower than `0.51.1`:

```bash
agentkit -v
```

Or:

```bash
ak -v
```

If it is not installed, or if the version is lower than `0.51.1`, install the TypeScript version of the AgentKit CLI with:

```bash
curl https://agentkit-cli.tos-cn-beijing.volces.com/install.sh | sh
```

> The migration command is recommended to use the TypeScript AgentKit CLI entry point `ak`, to avoid command-name conflicts with the `agentkit` command from a Python `uv` environment or `agentkit-python-sdk`. `ak` is configured automatically by the installation script and requires no extra steps.

### Environment Preparation

In the `ADP/workflow/` directory, copy `.env.example` to `.env`, then fill in the environment variables required for migration and deployment.

Before running, the AgentKit CLI automatically loads the `.env` file in the current execution directory. You do not need to manually run `source .env`. Therefore, you can write the environment variables directly into `.env` and avoid importing them manually each time. `CODEX_MIGRATE_MODEL_API_KEY` is used for the remote Codex Sandbox migration task, and `MODEL_AGENT_API_KEY` is used by the migrated application runtime to call the model.

Note: `--codex-api-key-env` and `--model-api-key-env` take environment variable key names. The CLI reads the corresponding real keys from `.env`. The `--codex-model`, `--model-id`, and `--model-base-url` parameters need actual values.

Volcengine:

```bash
VOLCENGINE_ACCESS_KEY=""
VOLCENGINE_SECRET_KEY=""

CODEX_MODEL_AGENT_NAME=""
CODEX_MIGRATE_MODEL_API_KEY=""

MODEL_AGENT_NAME=""
MODEL_AGENT_API_BASE="https://ark.cn-beijing.volces.com/api/v3"
MODEL_AGENT_API_KEY=""
```

BytePlus platform:

If you use the BytePlus platform, fill in the BytePlus AK/SK and model access configuration. In `.env`, replace the Volcengine account variables with `BYTEPLUS_ACCESS_KEY` / `BYTEPLUS_SECRET_KEY`, and set `CLOUD_PROVIDER=byteplus` and `BYTEPLUS_REGION`.

```bash
BYTEPLUS_ACCESS_KEY=""
BYTEPLUS_SECRET_KEY=""
CLOUD_PROVIDER=byteplus
BYTEPLUS_REGION=ap-southeast-1

CODEX_MODEL_AGENT_NAME=""
CODEX_MIGRATE_MODEL_API_KEY=""

MODEL_AGENT_NAME=""
MODEL_AGENT_API_BASE=""
MODEL_AGENT_API_KEY=""
```

### Create a Migration Task

`create` submits `any_input/` to the remote Codex Sandbox for migration. `--output ../any_output` is resolved relative to `any_input/`, and the final artifacts are written to `ADP/workflow/any_output/`.

```bash
cd <project_dir>/ADP/workflow

agentkit migrate any_input --framework any create --name any-test --output ../any_output \
  --codex-model <codex-model-name> \
  --codex-api-key-env CODEX_MIGRATE_MODEL_API_KEY \
  --model-id <VeADK-model-name> \
  --model-base-url <model-base-url-required-by-VeADK> \
  --model-api-key-env MODEL_AGENT_API_KEY
```

Equivalent command using `ak`:

```bash
cd <project_dir>/ADP/workflow

ak migrate any_input --framework any create --name any-test --output ../any_output \
  --codex-model ep-20260601142014-7hztz \
  --codex-api-key-env CODEX_MIGRATE_MODEL_API_KEY \
  --model-id ep-20260601142014-7hztz \
  --model-base-url "https://ark.cn-beijing.volces.com/api/v3" \
  --model-api-key-env MODEL_AGENT_API_KEY
```

After creation succeeds, the command returns a `job_id`. The actual task record for this example is stored in `any_input/.agentkit/migrate/jobs/<job_id>.json`, and the migration result has been downloaded to `any_output/`.

## Query and Download Results

Query the task status and download the final artifacts:

```bash
agentkit migrate any_input --framework any status --job-id <job_id>
```

Equivalent `ak` command:

```bash
ak migrate any_input --framework any status --job-id <job_id>
```

You can also use the positional argument form:

```bash
agentkit migrate any_input --framework any status <job_id>
```

Equivalent `ak` command:

```bash
ak migrate any_input --framework any status <job_id>
```

View local migration task records:

```bash
agentkit migrate any_input --framework any list
```

Equivalent `ak` command:

```bash
ak migrate any_input --framework any list
```

After the task succeeds, `any_output/convert_report.md` records the source application identification results, behavior analysis, generated files, validation conclusions, and subsequent deployment instructions.

## Optional: Local Debugging for the VeADK Project

Before deploying to AgentKit Runtime, you can enter `any_output/` to inspect the migration artifacts. It is recommended to focus on:

- `assistant/agent.py`: The migrated VeADK agent, including the hotel booking expert persona, the `北京饭店` recommendation rule, and the read-only boundary description.
- `.agentkit/agentkit.yaml`: AgentKit Runtime deployment configuration, including model, resource specifications, environment variables, and APMPlus configuration.
- `migration_metadata.json`: Source application information, preserved behavior, degraded behavior, and evaluation suite description.
- `eval/cases.json` and `eval/rubric.md`: Behavior validation samples and evaluation criteria for the migrated application.

The migration artifacts in this example have passed the static checks recorded in `convert_report.md`, including Python compilation, required file existence, `assistant.agent.root_agent` import, `main.app` import, and AgentKit configuration checks.

## AgentKit Deployment

After migration is complete, enter the output directory, confirm that `.agentkit/agentkit.yaml` is configured correctly, and then run:

```bash
cd any_output
agentkit release
```

Equivalent `ak` command:

```bash
cd any_output
ak release
```

In the actual test flow, `release` builds the image and publishes the Runtime. After publishing is complete, you can open the online test page in the AgentKit console to verify the agent response.

## Output Result

After migration is complete, the output directory usually contains:

- A VeADK / AgentKit Runtime project that can directly run `agentkit release`.
- `.agentkit/agentkit.yaml` deployment configuration.
- `assistant/agent.py` runtime code.
- `convert_report.md` migration report.
- `migration_metadata.json` migration metadata.
- `source_behavior_contract.json` source behavior contract.
- `eval/cases.json` and `eval/rubric.md` evaluation samples.

In this example output, the source workflow is converted into a VeADK agent named `hotel_booking_agent`. It preserves hotel booking consultation and Beijing hotel recommendation behavior, and when users request actual ordering, payment, or booking on their behalf, it explains that it can currently only provide recommendations and planning services.
